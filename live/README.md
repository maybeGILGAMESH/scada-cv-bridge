# Чтение щита с трансляции в реальном времени

Щит крутится на одном компьютере, а распознаётся на другом: картинка уходит
через KVM (Pi Zero 2) и приходит сюда видеопотоком. Скрипт видит только эту
картинку — ни модели, ни её чисел у него нет — и выкладывает прочитанное на
локальный сайт.

```
ПК-1: neft-hmi-cv.html ──HDMI──▶ KVM (Pi Zero 2) ──сеть/USB──▶ ПК-2: live/run.py
                                                                     │
                                                        http://127.0.0.1:8770
```

## Запуск

```bash
pip install opencv-python numpy
```

```bash
python live/run.py --source http://pikvm.local/streamer/stream
```

Другие источники кадров:

| `--source` | что это |
|---|---|
| `http://…/streamer/stream` | MJPEG-поток: так отдают PiKVM и mjpg-streamer |
| `snapshot:http://…/snapshot` | стример умеет только одиночный кадр — опрашиваем его |
| `0`, `1`, … | USB-карта захвата (UVC), номер устройства |
| `кадр.png` или `папка/` | файлы — отладка без железа |

Полезные ключи:

| ключ | зачем |
|---|---|
| `--port 8770` | на каком порту поднять сайт |
| `--no-normalize` | кадр уже 1920×1080 один к одному, масштаб искать не надо |
| `--only gauge,sevenseg_digit` | читать не весь щит, а только нужные классы — заметно быстрее |
| `--register-every 8` | как часто заново искать блоки (при просадке балла — вне очереди) |
| `--gauge-stride 3` | шаг грубого прохода по углам манометра; `1` — перебор всех углов |
| `--dump state.json` | писать каждое состояние в файл |

## Что происходит с кадром

**1. Кадр возвращается к масштабу щита.** Через KVM приходит не то, что рисует
браузер: картинка отмасштабирована под разрешение захвата, сдвинута полями,
пережата JPEG. `matchTemplate` не прощает масштаба, поэтому сначала ищется сам
щит — многомасштабным сопоставлением неизменного куска шапки (название куста и
скважины). Шапка не входит ни в один переставляемый блок, поэтому годится как
опора при любой компоновке.

Найденное преобразование держится, пока держится балл: пересчёт запускается,
только когда привязка начинает сыпаться — сменилось разрешение захвата, окно
передвинули, поток перезапустился.

На проверке с захватом 1280×800, где щит уложен в 1280×720 со смещением по
вертикали и пережат JPEG качества 70, калибровка находит масштаб 0,664 (точное
значение 1280/1920 = 0,667) и начало щита (0, 38) — ровно высоту чёрного поля.

**2. В кадре находятся блоки щита.** Не по координатам: из контрольного кадра
вырезается кусок блока целиком и ищется во всём кадре — грубо на уменьшенной
вчетверо паре, затем с уточнением на полном разрешении. Результат — сдвиг
каждого блока, он и показывается на сайте отдельной таблицей.

**3. Приборы читаются там, где блок нашёлся** — теми же приёмами, что и в
`cv_templates/match_templates.py`: манометр перебором углов, индикатор по
знакоместам, столбчатый и уровень по отличию от эталона «пусто».

## Сайт

| адрес | что отдаёт |
|---|---|
| `/` | страница с показаниями |
| `/events` | поток обновлений, Server-Sent Events |
| `/api/state` | последнее состояние одним JSON |
| `/frame.jpg` | последний нормализованный кадр |

Только стандартная библиотека Python: WebSocket тут не нужен, поток
односторонний, а SSE сам переподключается после обрыва.

Страница показывает не только числа, но и то, откуда они взялись: найденный
масштаб кадра, сдвиг каждого блока, балл привязки, время на кадр и сам кадр
после нормализации. Недостоверно прочитанное помечается пунктиром, а не
выдаётся за обычное значение.

## Как замечается перестановка блоков

Поиск блоков стоит около 0,45 с, поэтому идёт не на каждом кадре, а раз в
восемь (`--register-every`). Само по себе это опасно: переставь блоки — и
приборы продолжат читаться по устаревшим сдвигам, выдавая уверенные, но
неверные числа. Поэтому на каждом кадре проверяется один блок по очереди:
небольшой его кусок сопоставляется в окрестности ожидаемого места. Сдвинулся
или перестал узнаваться — полный поиск запускается немедленно, не дожидаясь
очереди. Балл привязки на сайте — всегда свежий: при пропуске поиска
показывается балл проверенного блока, а не сохранённый от прошлого раза.

## Скорость

Замер на синтетической трансляции (щит 1920×1080 уложен в захват 1280×800,
JPEG качества 70), обычный настольный процессор, читается весь щит — 82
объекта, из них шесть манометров с перебором углов:

| кадр | что происходит | время |
|---|---|---:|
| первый | полный поиск блоков, полный перебор углов | 8,8 с |
| следующие | углы ищутся рядом с прошлыми | 1,7–2,0 с |
| кадр со сменой компоновки | замечено проверкой, полный поиск блоков | 2,0–2,7 с |

Стрелка между кадрами далеко не уходит, поэтому угол ищется сначала рядом с
прошлым значением: вместо 55 сопоставлений выходит девять. Если рядом ничего
уверенного нет — честный откат на полный перебор, подсказка сама по себе
ничего не решает.

Точность через такую трансляцию: манометры в пределах 0,6 % шкалы, все шесть
семисегментных индикаторов читаются посимвольно верно — во всех четырёх
компоновках.

Если нужно чаще:

* `--only gauge,sevenseg_digit,bargraph` — читать лишь то, за чем следите;
* `--register-every 20` — реже искать блоки, если компоновку не переставляют;
* `--gauge-stride 3` — грубый проход по углам, вдвое быстрее. Проверено
  прогоном контрольного набора: 932/938 против 933/938, единственная потеря —
  манометр на самом верху шкалы. Поэтому по умолчанию выключено.

## Чего этот конвейер не делает

* Не читает состояние из модели щита. Единственный вход — пиксели.
* Не управляет щитом: связь односторонняя, с трансляции только читают.
* Не переживает поворот картинки. Захват должен быть без поворота: масштаб и
  сдвиг снимаются калибровкой, поворот — нет. Это ограничение `matchTemplate`,
  а не конкретно этой обвязки.
